# 新项目接入 4yi App Marketplace：开发者快速上架指南

本文适用于把已有 GitHub 项目改造成通过 4yi App Platform 运行的 Web 应用。以每个组织安装独立实例（Dedicated app）为主要路径；共享实例需要另行设计和验证租户隔离。本指南基于 Teardown 的 DEV 接入实践，平台页面和发布门槛以目标环境当前显示为准。

## 准备信息和权限

开始前确认：

- 项目仓库 URL、可读取的分支、许可证、现有启动方式及必要的外部依赖。
- 一个可用于 DEV 的 4yi 组织和账号、可用的模型和额度，以及可执行 Marketplace Import 和发布的管理员。开发者没有管理员权限时，与管理员协作完成导入和发布。
- 应用功能边界、需要持久化的数据、是否有用户上传或执行不可信内容、预期 CPU／内存和磁盘需求。
- 安装方式：每组织独立实例还是共享实例；同一个实例内用户之间的数据是否共享。不要因为采用独立实例就假定实例内各用户的数据自动隔离。

先定义一个可验收的最小流程，例如“输入描述 → 提交生成 → 查看状态 → 打开结果”，再扩展其他功能。确认原项目是否包含真实业务能力：一个界面或模型生成示例不代表原项目所有功能已经接入。

## 1. 改造项目为 Web 服务

1. 保留原项目核心逻辑，添加浏览器界面和后端 API；CLI／桌面交互改为可通过 HTTP 触发的操作。
2. 长时间任务使用后台任务和状态查询，提供失败信息、刷新和必要的取消能力。页面刷新后应重新读取任务，而非只依赖浏览器内存。
3. 服务监听容器的 `0.0.0.0` 和配置的端口；提供轻量的 `/healthz`，健康检查无需模型调用或用户会话。
4. 数据写到可配置的持久化目录；不要依赖容器临时文件。确认以非 root 用户运行时，挂载目录有写权限。
5. 提供 Dockerfile、确定可重复安装的依赖，避免写死开发机路径或 CPU 架构。按目标环境要求构建镜像并确认启动。
6. 验证暂时断连、服务重启或从休眠唤醒后，页面能够恢复；成功读取后清除过期的加载错误，同时保留仍然有效的操作错误。

本地检查示例，请将端口、启动命令和路径替换为项目实际值：

```bash
docker build -t my-app:local .
docker run --rm -p 3000:3000 my-app:local
# 在另一个终端执行：
curl -fsS http://localhost:3000/healthz
```

需要环境变量或持久卷时，使用本地测试配置启动；不要将真实令牌写入镜像、Git 或命令输出。

## 2. 接入模型与访问身份

### 模型

应用按配置读取平台网关地址、安装实例的令牌和所选模型；不要把个人 API key 固定在代码或部署声明中。Teardown 使用 `OPENAI_API_BASE`、`OPENAI_API_KEY`、`TEXT_MODEL`。模型不一定兼容所有协议和参数，须在目标环境验证。

导入后检查 proposal 的 Platform Runtime：网关地址和密钥的环境变量映射、模型槽位、默认模型和类型是否正确。`4yi-app.json` 的 `models` 声明只会补充平台已从项目识别的同名槽位；应用未读取对应变量时可能产生警告，不能假定仅写声明就完成模型接入。实际安装时再核对用户可选模型及组织额度，并通过真实模型完成一次任务。

### 路由与数据授权

4yi 路由负责用户访问认证，应用通常不需要另建登录页面。但应用如果按用户区分任务、文件或权限，仍需要可信用户身份，并在每次读取、修改和预览时执行授权。不要直接信任客户端可伪造的普通身份请求头，也不要把模型网关令牌当作用户身份。

Teardown 使用 4yi 路由签名身份：应用实际校验签名，平台为安装实例注入校验所需配置。若新应用采用此机制，参考 [Teardown 服务端实现](https://github.com/4yi-ai/teardown/tree/main/web)，并与平台管理员确认目标环境已部署兼容版本；仅设置 `FOURYI_ROUTER_IDENTITY_REQUIRED=1` 并不能替应用完成签名校验。健康检查和业务接口如何区分，也要按实际实现验证。不要记录或输出签名密钥。

## 3. 添加仓库根目录部署声明

在仓库根目录创建 `4yi-app.json`。以下是单 Web 服务的示例；按项目修改 Dockerfile、端口、资源、存储和模型：

```json
{
  "version": 1,
  "services": [
    {
      "name": "web",
      "dockerfile": "Dockerfile",
      "context": ".",
      "route": "public",
      "port": 3000,
      "healthPath": "/healthz",
      "storage": { "sizeGb": 1, "mountPath": "/data", "fsGroup": 1000 },
      "resources": { "cpu": 1, "memoryMb": 2048 }
    }
  ],
  "models": [
    { "env": "TEXT_MODEL", "type": "chat", "default": "gpt-6-luna" }
  ]
}
```

- `version` 为 1；`services` 非空，且恰好一个服务为 `public`，其他服务可为 `internal`。
- `dockerfile` 和 `context` 必须指向仓库中存在的路径，`port` 和 `healthPath` 要与服务实际运行一致。声明校验拒绝未知字段；不要把令牌写入 `env`。
- 示例的 1 核、2 GB、1 GB 卷是 Teardown 使用过的量级，不保证适合其他项目；不需要存储或模型时可省略相应配置。`fsGroup` 必须和实际容器权限相匹配。
- 默认模型只是示例，确认目标环境存在并可供安装组织使用；若项目使用不同名称，保持代码、声明和导入 proposal 一致。
- 如果服务需要 Teardown 的路由签名机制，在真实实现校验后再加入其相应配置；不要机械复制开关。

详细格式和规则见 [部署声明设计](https://gitlab.bieases.com/dop/xclaw/-/blob/main/docs/superpowers/specs/2026-08-03-marketplace-import-app-declaration-design.md)；可参考 [Teardown 的声明](https://github.com/4yi-ai/teardown/blob/main/4yi-app.json)。

## 4. 提交代码并在 DEV 导入

1. 运行项目测试、构建镜像并执行本地健康检查；提交代码并推送到平台可读取的 GitHub 分支。记录提交 SHA。
2. 管理员进入目标 DEV 环境的 **AI Marketplace Import**（DEV 示例：`/admin/marketplace/ai-import`）。在 **GitHub Source** 填写仓库 URL 和分支，选择 Dedicated 类型并创建导入任务。
3. 执行 **Run Analyze**。查看扫描结果、blocker、风险和仓库声明是否生效。
4. 审核 proposal：服务拓扑、Dockerfile／context、路由、端口、健康检查、CPU／内存、存储、模型槽位及网关变量映射、密钥分类和定价。更正方案或代码；代码更改后重新分析并核对实际使用的提交。
5. 在审核通过后选择 **Apply**，然后执行 Release／构建部署。跟踪构建日志、服务启动和 smoke test，确认运行的是预期提交对应的版本。
6. 查看 **Publish Gate**，按页面要求完成 smoke、billing dry-run、租户隔离及其他检查。`Certify` 表示人工确认隔离，必须基于真实证据填写，不应自动认证或将模拟测试描述为真实多账号测试。
7. 执行 **Publish**，在 Marketplace 管理中检查展示资料、费用、状态，以及目标套餐和组织白名单。页面名称及权限以实际环境为准。

按平台实际门槛安排测试顺序：有的平台允许发布者先测试未公开版本；有的真实消费者安装需要先开放测试范围。对未完成的测试如需受限 DEV 试用，应由有权限的负责人明确批准并记录限制，不要把 DEV 测试授权视为生产发布授权。

## 5. 用真实安装验收

在目标 DEV 组织从市场进入该应用，安装时选择模型，打开应用并完成：

- [ ] 应用启动，健康检查通过，用户能通过 4yi 打开；实例休眠时能唤醒。
- [ ] 创建一个真实任务，完成后查看结果并操作至少一个主要控件；刷新后任务仍可读取。
- [ ] 确认模型调用使用安装时选择的模型、该组织的令牌和额度，不使用开发者个人密钥。
- [ ] 对有持久化要求的应用，重启／更新后检查数据；验证非 root 容器对挂载目录可写。
- [ ] 用不同真实组织和账号验证访问授权及数据隔离；同组织多用户场景也按产品预期验证。记录未覆盖场景。
- [ ] 验证未授权直连、伪造身份、预览／下载／API 等路径不能绕过应用所需的数据授权。
- [ ] 对执行用户代码、生成 HTML、上传文件或浏览器自动化的应用，单独验证隔离、权限、网络和资源限制。
- [ ] 确认目标用户在市场看得到应用，安装、打开及应用更新的实际版本正确。

保留发布版本或提交 SHA、测试组织和账号、时间、结果、已知限制与失败日志（脱敏）。不要记录访问令牌、模型密钥或用户隐私数据。Teardown 已验证个人 DEV 安装可生成并操作结果；其早期跨组织和同组织多账号测试存在未完成项，不能据此替代新项目的隔离验收。

## 常见问题

| 现象 | 优先检查 |
| --- | --- |
| 导入声明无效 | JSON、未知字段、Dockerfile／context 是否存在、是否恰好一个 public 服务、平台是否支持所用字段。 |
| 构建通过但容器不健康 | 监听地址和端口、`/healthz`、启动日志、架构、环境变量和持久卷写权限。 |
| 没有模型可选或调用失败 | proposal 的模型槽位和网关变量、目标组织的模型权限与余额、模型协议与参数；不要输出令牌。 |
| 管理员能看到，其他组织看不到 | 上架状态、smoke／发布门槛、套餐和组织白名单、当前组织及缓存；确认目标环境是 DEV。 |
| 能打开但任务读取失败 | 实例是否休眠或正在唤醒、路由与签名身份配置、任务 API 和服务日志；恢复后再验证错误提示是否清除。 |
| 更新后仍是旧版本 | 核对 release 与镜像，确认消费者实例是否需要从市场执行“更新应用”；发布者部署成功不代表所有已安装实例自动升级。 |
| 重新构建后应用不可见 | 检查新 release 的 smoke 和上架状态；先确认检查通过，再按管理员流程恢复展示。 |

## 完成标准与交付

向负责人交付：仓库和提交 SHA、DEV 应用入口、发布版本、使用的资源配置、安装和测试步骤、验收结果与已知限制。只有对应环境的发布门槛和实际测试完成，才能称该环境上架完成；DEV 上架不代表已发布到生产。
